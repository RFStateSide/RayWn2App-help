Station API v1 developer reference

This is the version 1 contract for monitoring integrations. Use the operator setup topic to start the host and create a token first. API v1 is independent of the application release, WSS pairing protocol and MQTT payload schema. This guide and its OpenAPI file describe the existing read-only implementation; they add no control permissions.

Files and working examples

The machine-readable contract is docs/api/openapi-v1.json (OpenAPI 3.1, JSON format). The matching developer document is docs/api/v1.md. Credential-free examples are examples/api/client.py, readings.sh and node-red-http.json, with setup in examples/api/README.md. These are standalone client examples for integrators. No example contains an account, bearer token or private key.

Compatibility policy

The URL prefix is /api/v1 and every JSON response has schema equal to 1. The OpenAPI document version is 1.0.0. Within v1, clients must tolerate unknown response fields and human-readable labels. New optional response fields may be added. Removing/renaming required fields, changing their types, units or defined enum values, altering null meaning or changing existing history column semantics requires a new API version. Clients must not send guessed query parameters: unknown, repeated or explicitly empty parameters currently return 400.

Connection, TLS and authorization

Use HTTPS with HTTP/1.1 on the explicitly enabled API listener, normally port 47828. WSS normally uses 47827 and does not accept HTTP API requests. API listeners default OFF. Use the configured port rather than assuming defaults. One request is served per connection; do not rely on keep-alive, HTTP/2 or pipelining. Redirects are not part of the API.

Verify the certificate chain, validity dates and server name. A self-signed station certificate must be trusted explicitly. For an existing certificate without a matching DNS/IP name, the Python example supports an independently verified exact SHA-256 certificate pin in addition to chain/date verification. It verifies the pin before sending credentials. Never disable TLS verification or automatically accept a replacement certificate.

Send the exact header Authorization: Bearer TOKEN on every request. The opaque token is 64 lowercase hexadecimal characters and grants selected device identities. It grants all read-only v1 routes for those devices; there is no per-channel or separate history permission. A WSS pairing code, cookie or URL token is not API authentication. Tokens have no configured expiry and remain valid until revoked or the token store is replaced. Keep them in a consumer secret store. The host retains hashes, not recoverable bearer secrets.

Token issuance and revocation are local operator actions. Desktop controls are on Tools > Remote Station > HTTPS / JSON API. Linux service commands are --api-token DEVICE (repeat for several devices) and --api-revoke-all. They are not HTTP endpoints. API revocation leaves WSS pairings unchanged; stopping the host closes both listeners. Maximum eight token grants, each with up to sixteen devices.

Endpoint reference

No query parameters are accepted.

HTTP 200 response model: StatusResponse. Declared error statuses: 400, 401, 405, 431, 503.

Responses, time and freshness

All JSON responses contain schema and server_utc. The latter is the host UTC response time, not a measurement timestamp. received_utc is host receipt time; WN-2 samples do not supply an independently synchronized station timestamp here. age_ms uses host elapsed time and is -1 before the first sample. The frame counter is a decimal string to avoid numeric precision loss and can reset when a session is reopened. It is not globally unique. Multiple devices have their own sample times.

HTTP 200 only confirms request success. Use fresh, age_ms and per-value validity. connected alone is insufficient. The current host freshness window is 1500 ms. At receipt, expire a displayed result after at most max(0, 1500 - age_ms) milliseconds of local elapsed time. Never keep a last-good value labelled live if polling stalls. An empty devices array is a successful authorized result with no currently configured visible sessions.

JSON null means unavailable, invalid or nonfinite. Zero is a measured value and must remain zero. Low-RF SWR and return loss can be null while valid power values remain near zero. Four power_status entries correspond to forward average, reflected average, forward peak and reflected peak, in that order. A clipped or invalid power path is null. source identifies physical, simulated or replay measurements; consumers must select explicitly rather than combine them by channel number.

RF keys ending in _W are watts; return_loss_dB is dB and swr is a ratio. DC and analog values are in inputs with explicit configured units, including temperatures. Digital input values include configured inversion. Power peaks are the host measurement peaks, not a client software peak hold. profile is an identity label, not a complete calibration audit hash. status, state and protection.description are human-readable and can change wording. An unknown protection trip state is never a confirmed healthy relay.

RfChannel

Field (required)JSON typeMeaning
channelintegerOne-based RF channel.
couplerstringConfigured coupler model; None means not configured.
profilestringConfigured calibration profile identity; not proof of physical qualification.
statusstringHuman-readable measurement condition. Do not branch on exact wording.
power_statusarray of stringValidity in forward average, reflected average, forward peak, reflected peak order.
forward_average_Wnumber or nullForward average power in watts, or null if unusable.
reflected_average_Wnumber or nullReflected average power in watts, or null if unusable.
forward_peak_Wnumber or nullForward peak power in watts. Host measurement, not a client software-held peak.
reflected_peak_Wnumber or nullReflected peak power in watts. Independent of forward peak.
swrnumber or nullSWR ratio; null at Low RF, invalid data or nonfinite result.
return_loss_dBnumber or nullReturn loss in dB; null if invalid/nonfinite. Can be negative.
average_powerobjectOptional provenance: policy (legacy or explicitly selected raw-usb-host-estimate), effective forward/reflected processing, and swr_basis (legacy-average or explicitly selected paired-peak). Watt readings are already processed; clients must not apply the estimate again. An active reference curve bypasses estimation for its direction. Other processing states identify the low-level gate or unavailable inputs. Firmware is not automatically inferred; modulated-signal accuracy remains unqualified.
swr_calculationobjectOptional SWR/return-loss provenance. Legacy average-power ratio is the default. Paired-peak uses calibrated forward/reflected peaks from the same USB acquisition frame, selecting the median-ratio pair from up to three valid frames within 1000 ms. This independent RF StateSide filter does not reproduce the vendor host algorithm. Invalid, low-RF or clipped input clears history. Peak measurements and software-held peaks are not modified. Same-frame grouping does not prove simultaneous hardware acquisition. No firmware capability is inferred. The chosen pair can predate the current frame; inspect age_ms and frame. Unknown optional fields must be tolerated.
power_conversionobjectOptional per-device/channel/coupler calculation provenance. Legacy uses the saved scalar/reference profile unchanged. Explicit wavenode-host-v1 is a separate factory detector conversion for LP-1, standard HF and channel-specific HF-8KW families; saved scalar coefficients are bypassed but not modified, ADC zeros are retained. Active reference matching preserves the whole channel legacy conversion. Unsupported models remain on the stored profile. Per-frame only: no original-host display-history filtering or firmware inference. Physical RF accuracy is unqualified. Consumers must not apply this processing again. Eligible new supported coupler configurations select host factory conversion, corrected detector average and paired-peak SWR; existing saved policies retain their behavior. These preferences do not establish physical RF accuracy. All nine current couplers are mapped; L/M-1, CS-1, UHF-220MHz and UHF-70cm share the HF family by owner-approved rated-range mapping, identified in processing metadata and not independently physically qualified. Historical 8KW/HF-UHF keys are retained; 20KW factory parity is deferred.

History paging and CSV export

List segments for one granted device and choose an exact returned segment name. Start the first page with offset=0 and end=0. Preserve the returned end for every later page and use next as offset until more is false. Do not calculate byte offsets from row counts or CSV line lengths. A page contains at most 64 rows and approximately 120 KiB of row data. Segments are limited to 2 MiB. New appends beyond the captured boundary are excluded from the export; refresh for later samples. Only complete recorded rows are returned.

The columns array defines the order of all 28 string cells per history row. Empty measurement cells mean unavailable; they are not JSON null and must not become zero. channel is a one-based string in rows; query channel=0 selects all channels. recorded_utc is recorder time, sample_utc is host sample receipt time, sequence is the session frame counter, and digital_raw_bits is the raw input mask before configured inversion. Analog values have separate unit cells. These are recorded measurements, not interval aggregates or an exhaustive event stream.

On 409, discard the partial export and refresh the segment list; do not silently join a replacement file or reset end midway. On network/authentication failure, discard partial output. The Python example writes a private temporary file and publishes the completed CSV atomically. It preserves missing cells and guards text cells against spreadsheet formula execution. Retention is segment/size based and does not guarantee 30 days. There is no date-range query, aggregation, arbitrary path access or recording-control endpoint.

Errors and consumer behavior

HTTP statusMeaning
400Malformed request, unsupported body, unknown/repeated/empty query parameter, invalid cursor or segment.
401Missing, malformed, revoked or unrecognized bearer token.
403Requested device is outside the token grant.
404Unknown route or explicitly selected granted device is no longer configured.
405Authenticated request uses a method other than GET.
409History file unavailable, rotated, truncated or incompatible; refresh the segment list.
431Request headers exceed 8192 bytes.
503History not configured, history worker/response capacity limit or certificate condition. A configured history directory failure can return 409.

Errors contain schema, server_utc and error. Error text may be a short code or a human-readable history diagnostic; do not treat it as a fixed enum. Malformed headers/body can be rejected before authentication or method checks. A TLS handshake failure or a closed/overloaded connection can produce no HTTP response at all. HTTP 401 includes WWW-Authenticate; 405 includes Allow: GET.

Use a modest polling interval such as one second. Back off after transport failures or transient 503; avoid repeated retries for 400, 401 and 403 until configuration is corrected. For a 409 history error, refresh rather than retrying a stale cursor. Do not forward tokens on redirects, put Authorization headers in Debug, or cache telemetry. Responses use Cache-Control: no-store. No browser CORS access, OAuth, hardware controls, remote scope or spectrum endpoint is provided.

Limits and demonstrated scope

The listener accepts eight concurrent connections, two history workers, 8192 request-header bytes, a ten-second connection deadline and at most 256 KiB per JSON response. History runs away from the live telemetry event loop. This is advisory monitoring, not a hardware interlock or delivery guarantee.

The accepted API was tested with two emulators and two WSS clients on Windows, an isolated Ubuntu service, and physical Pi 5 VCP CH2 monitoring from Windows alongside WSS. The physical check verified telemetry delivery and history agreement using the host profile, not absolute power calibration. Physical D2XX API and reboot qualification of this addition remain pending. REM-09 still has other outstanding capabilities.

Examples and validation

See the examples topic for curl, Python and a standalone Node-RED HTTP Request flow. The Python client uses only the standard library. The flow uses core nodes, explicit environment-selected source/channel, verified TLS, sanitized Debug output and an independent expiry check. It does not change existing dashboards. Node-RED and Python UI consumers must clear stale displays on polling failures.

Maintainers validate docs/api/openapi-v1.json with the dependencies listed in docs/api/requirements-validation.txt. Run scripts/build-api-reference.py --check and tests/api_v1_documentation_tests.py. For real response validation, set RAYWN2_API_CONTRACT_CAPTURE_DIR while running raywn2_station_api_tests, then pass that directory using --fixtures. Exported fixtures contain only response bodies and route paths, never headers, request query values or bearer tokens. The contract should be checked whenever endpoint fields change.
