API v1 working examples

These examples are for an operator or integrator building a monitoring display. Set up the HTTPS host and token first. The complete source examples are in examples/api, with the OpenAPI file in docs/api/openapi-v1.json. These standalone client examples are intended for integrators.

Python: current CH2 and history

The sample client.py needs Python 3.9 or later and uses its standard library. It prompts privately for the token when one is not supplied by your protected process environment. Set your own station name, exact granted identity and trusted certificate path:

To keep the commands short, first set the process environment values RAYWN2_API_URL, RAYWN2_API_CA and RAYWN2_API_DEVICE to those station values. The Python client reads them as defaults. Then run:

python examples/api/client.py status
python examples/api/client.py --channel 2 watch --count 10
python examples/api/client.py segments

The watch output preserves null and zero and reports remaining freshness time. A display consuming it must expire old values while requests are pending. Request failures clear the next observation. The watch command prints JSON observations for a consumer to display.

Select an exact returned segment name and export it:

python examples/api/client.py --channel 2 export --segment NAME --output ch2.csv

Replace NAME with an exact returned segment name.

The example retains a fixed history boundary, filters source/channel and discards an incomplete export after failure. Blank cells remain blank. Existing output files are protected unless --overwrite is explicit. Full instructions are in examples/api/README.md.

curl: one reading request

In a POSIX shell with curl, populate RAYWN2_API_TOKEN from your private credential mechanism. Set RAYWN2_API_URL, RAYWN2_API_CA and RAYWN2_API_DEVICE, then run:

sh examples/api/readings.sh

The script verifies TLS, does not follow redirects and uses an owner-private temporary header file rather than putting the token on curl's command line. Do not enable shell tracing or share the process environment.

Node-RED: HTTP without MQTT

  1. Import examples/api/node-red-http.json into a separate new tab, preserving your current flows.
  2. Supply the process environment values RAYWN2_API_URL, RAYWN2_API_TOKEN, RAYWN2_API_DEVICE and RAYWN2_API_CHANNEL. Do not type a real token into a shared flow or Function node.
  3. Configure the HTTP Request node's trusted certificate/CA. Keep certificate verification enabled and use a name matching the certificate. The example uses system trust until a private CA is configured.
  4. Deploy your new tab and press Poll once. Only Selected CH readings ONLY should feed Debug or your presentation. It strips the private headers. Do not expose the raw Prepare/HTTP messages.
  5. For continuous readings, set Poll to repeat every one second. The independent expiry check clears values after freshness expires, even if a request stalls. Its one-second check granularity can add up to one second. No dashboard add-on is needed.

The output includes available, selected device/channel, source, sample time and the five RF readings. Unavailable values are null. Low RF can be fresh while SWR is null. The flow does not reuse an old SWR or treat missing power as zero. No existing Ubuntu flows are changed by these examples.

Certificate identity and failures

Use a certificate-matching server name by default. For an existing certificate without a matching name, the Python client can use --fingerprint together with --ca. It validates the trusted chain and dates and checks the independently verified exact fingerprint before sending the token. The standard Node-RED HTTP example requires a matching certificate name. Never disable verification.

Stop and correct configuration after 400, 401 or 403. Back off for temporary failures. Refresh history selection after 409. HTTP success alone is not proof of fresh measurements. See the developer reference for the full field, error, limit and versioning contract.
